## 二、详细发现

### 1. 门店与距离（query-nearby-stores）

- 按「城市 + 关键词」区域搜索（如 北京/国贸），返回字段：
  `storeCode / storeName / address / distance(米) / businessStatus / businessStartTime / businessEndTime / reservation / reservationTimeOptions`
- 实测距离精度合理：269m / 394m / 538m / 649m / 729m（国贸商圈）；深夜营业门店同样返回。
- `longitude/latitude` 返回 0.0（点餐链路不提供坐标）——**排序用 distance 即可，无需坐标**。
- 门店可带「预约时段」（含"宵夜 22:14–22:46"这类时段）→ 深夜有「宵夜菜单」概念，影响点单与价格。

### 2. 菜单与价格（query-meals）

- 结构：`categories[]`（分类）+ `meals{code → {name, currentPrice, originalPrice, discountType, withOrder, canWithOrder, tags}}`
- 现成信息：
  - 划线价/立省文案（如"麦辣鸡腿汉堡三件套 33.5，划线 46"）；
  - 促销标记：`discountType = 促销优惠 / 随单购麦金卡优惠 / 早餐卡优惠…`；
  - 随单购对象（`withOrder.cardId/specId`）；
  - 分类里自带「500 大卡套餐」——健康路线可借力。
- **注意**：菜单因门店而异、因时段而异；菜单快照价与实时算价可能不同（实测：巨无霸 25.5→26、薯条 13.5→14.5）。→ **一切以实时算价为准**。

### 3. 优惠券（三层结构 + 三个硬约束）

三层：
| 层 | 工具 | 内容 |
|----|------|------|
| 可领券池 | `available-coupons` | 标题/状态/图片（**无券码，不能直接用于算价**） |
| 领取 | `auto-bind-coupons` | 一键领取，返回 couponId/couponCode |
| 券包/门店可用 | `query-my-coupons` / `query-store-coupons` | 券码、有效期、适用商品、标签（含"到店专用"） |

三个硬约束（重要）：
1. **一单一张券**：多张券同单直接报 600022。多券想用就必须**拆单**（代价：多次下单/多次取餐）。
2. **券-门店-时段强绑定**：同一张券在不同门店可用性不同；门店打烊后其可用券列表变空。→ 每次询价必须实时 `query-store-coupons`，不可缓存。
3. **券商品编码独立**：算价时带券的商品需使用**券自己的 `products[].productCode`**（实测 `9900000119` 通过，菜单编码 `507411` 被拒：「促销规则不支持该商品」）。

### 4. 算价器（calculate-price）—— 引擎核心

- 入参：门店、场景（orderType/beType）、商品列表（可带券/特调/套餐子项）、预约时间（可选）。
- 返回（分单位）：`原价 / 优惠额 / 现价 / 逐项小计 / takeWayList（堂食·外带）/ 各种费用位（配送费·打包费·餐具费，到店场景为 0 或空）`。
- 成功案例：
  - 无券（宵夜时段）：巨无霸 26 + 中薯条 14.5 + 可乐 9.5 + 巨无霸三件套 37 = **¥87**；
  - 带券（预约次日）：美式中杯 ¥19 → **¥13.3**（与券包标注的"用券价格"一致，优惠 570 分）。
- 失败案例（均为有效边界）：
  - 「门店暂停营业」（打烊后算价被拒）→ 预约单可绕过；
  - 「暂不支持多张券使用」；
  - 「促销规则不支持该商品」（券与商品编码不匹配）。
- **关键实证（本项目存在意义的直接证据）**：「麦咖啡冰美式中杯」直接买促销价 **¥11.9**，而用「7折券」为 **¥13.3** → **用券反而多花 ¥1.4**。→ 引擎必须对"用券/不用券"候选分别试算后取优，不能"有券就用"。
- 待确认：同单传入菜单编码与券编码两个"美式"，返回被合并为一条（疑为同一商品双编码的去重），Phase 1 需进一步确认映射关系。

### 5. 外卖链路（阻塞）

- `delivery-query-addresses` 返回空数组——**账号还没有配送地址**，`delivery-query-stores` / 外卖算价无法继续。
- 已获取 `delivery-create-address` 参数结构（城市/联系人/性别/手机号/地址/门牌号）。
- → **产品设计要点**：通用 Skill 必须处理「新用户无地址」路径：引导创建 → 再查可配送门店 → 算价（含配送费/打包费）。

## 三、对设计的影响（相对原计划的更新）

1. **券优化逻辑重写**：候选枚举以「单」为单位，每单最多一张券；新增候选类型「**拆单策略**」（多张券拆多单使用），输出时明确标注"需分 N 次下单"的成本。
2. **试算必须双向**：每个候选方案同时试算「用券」与「不用券」两个版本，取实付更优者（有实证支撑）。
3. **实时性红线**：门店价、券可用性、营业状态全部实时查询，禁止缓存跨时段复用。
4. **预约场景可用**：支持"明天早餐怎么吃最划算"这类预约单（`reservationDate`）。
5. **到店排序**：直接用 `distance`；无需外部地图/坐标。
6. **外卖路径**：以「地址簿/创建地址」为起点；配送费/打包费从算价返回中读取。
7. **健康路线**：菜单自带「500 大卡」分类 + 营养表（list-nutrition-foods），后续做约束筛选。
